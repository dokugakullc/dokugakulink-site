# お問い合わせ保存機能 運用・プライバシー文書

対象：`docs/gas/contact-store-webhook.gs`（GAS）＋ `src/app/api/contact/route.ts` /
`src/lib/contactHandler.ts` / `src/lib/contactStoreClient.ts` / `src/lib/contactStorePayload.ts` /
`src/components/ContactForm.tsx`（Next.js）。

問い合わせ情報には**氏名・会社名・メールアドレス・お問い合わせ内容**（個人情報）が含まれる。
本書は保存・保持・削除の**運用ルール**を定める。**保持期間は 2026-08-02 に Owner が正式採用**（本書 §6）。
法的妥当性は Owner／法務が最終確認する（本書は断定的な法解釈を避け、公式資料を根拠として提示する）。

## 0. 現在の有効化状態（2026-08-02 時点）

- Contact 保存機能は **Production で有効**（`CONTACT_STORE_URL` / `CONTACT_STORE_SHARED_SECRET` が Production に設定・Owner 意図的）。
- **Preview には設定していない**（Preview は handler が検証前に 503 で停止し、保存もメールも行わない）。
- 未設定環境（Preview / ローカル）では従来どおりメール通知のみ（後方互換）。

## 1. 保存の目的

- お問い合わせへの**回答**、**本人確認**、対応状況（`status`/`owner`/`responded_at`）の**対応履歴管理**。
- **不正利用・迷惑送信の防止**、および傾向把握（種別 `contact_type`・流入 UTM）による**サービス・対応品質の改善**。
- 目的外利用はしない。広告配信・営業メール送付・第三者提供の目的では利用しない。

## 2. 保存項目（実装と一致）

`contacts` シート（ヘッダー名基準）：
- 利用者提供：`name`（氏名）/ `company`（会社名・任意）/ `email`（メールアドレス）/ `contact_type`（お問い合わせ種別）/ `message`（お問い合わせ内容）
- システム付与：`timestamp`（受付日時・JST）/ `reference`（受付番号）/ `submission_id`（冪等キー）/ `contact_id`（内部ID）
- 技術情報：`user_agent`、`source`、`utm_source`/`utm_medium`/`utm_campaign`/`utm_content`/`utm_term`/`fbclid`/`landing_url`/`referrer`
- 対応管理：`status`（既定 `未対応`）/ `owner` / `responded_at` / `is_test` / `created_by` / `schema_version`
- `subject` 列は現状**常に空**（クライアント・ハンドラは送らない。将来分類用の予約列）。
- **`token`（共有シークレット）は保存しない**（列に存在せず、応答・ログにも出さない）。長さ制限・制御文字（CR/LF/tab）除去あり。

## 3. 保存先

- `info@dokugakulink.com` 所有の Google スプレッドシート（`contacts` タブ）。**アクセス権限を制限したクラウドサービス**（Google 提供のサービスを含む）で保管する。
- Google は「委託・クラウド利用」として扱い、**必要かつ適切な監督**を行う（個人情報保護法 第25条 委託先の監督）。第三者提供として断定しない。

## 4. アクセス権限の原則

- 閲覧・編集権限は**対応に必要な最小人数**に限定する。**共有リンクを一般公開しない**（「リンクを知っている全員」不可）。
- 外部への**エクスポート・共有は Owner 承認制**。ダウンロードした CSV/コピーも同水準で管理する。
- **Secret はシートへ保存しない**（Vercel 環境変数と GAS Script Property のみ）。

## 5. 最終対応日の定義

- **最終対応日**＝当該問い合わせに対して**最後に対応（返信・処理）を行った日**。シート上は `responded_at`（対応時に運用者が記入）で表す。
- `timestamp` は**受付日時**であり最終対応日ではない。`status` は対応状態（`未対応`/対応中/完了 等）。
- **注意（起算日の判定不能）**：`responded_at` は挿入時は空で、運用者が対応時に記入する。未記入（未対応・記入漏れ）の行は最終対応日を機械的に確定できない。**推測で自動削除しない**（§14・自動削除の別承認条件）。

## 6. 保持期間（2026-08-02 Owner 正式採用）

1. **通常の問い合わせ**：最終対応日から**1年間**保管。
2. **未対応・対応中**：対応完了まで保持し、**最終対応日から1年間**。
3. **営業・迷惑送信・明らかなテストデータ**：確認後**90日以内**に削除。
4. **契約・請求・紛争対応等、別の保存理由がある情報**：必要な情報だけを適切な管理先へ移し、その目的に必要な期間だけ保管する。問い合わせ管理シート側は通常ルール（1年）で削除する。
5. **本人からの削除等の申し出**：本人確認と保存の必要性を確認し、法令上・業務上の保持理由がなければ期限前でも対応する。
6. 保存の必要がなくなった情報は、適切な方法（復元不可能な手段）で削除する。

> 公式根拠（§18）：個人情報保護法は保存年数を一律に定めていない。利用する必要がなくなった個人データは
> **遅滞なく消去するよう努める**（法第22条・努力義務）。上記は当社の運用ルールであり、法定の保存年数ではない。

## 7. 営業・迷惑送信・テストデータの扱い

- テストデータは `is_test = TRUE` で識別（メールの `+test`/`+lp-test`/`+meta-test` マーカー・`TEST_MARKERS` で調整）。
- 営業・迷惑送信・テストと**確認できたもの**は確認後 **90日以内**に削除。KPI・分析は `is_test = FALSE` のみ集計。

## 8. 契約・請求・紛争等への移管手順

1. 保管理由（契約・請求・紛争・法令上の必要）と、そのために**本当に必要な項目だけ**を特定する。
2. 必要な情報を**適切な管理先**（契約・請求・法務の管理場所）へ移し、その目的に必要な期間だけ保管する。
3. 問い合わせ管理シート側の該当行は、**通常ルール（§6-1）で削除**する（二重保管を残さない）。

## 9. 毎月の確認（担当・日）

- **毎月1回**、期限到来分を確認する（確認日・担当者は Owner が指定。例：毎月初営業日／担当＝Owner）。
- 確認では削除対象（§6）と、複製・書き出し・ダウンロード・バックアップ・ゴミ箱（§11）を点検する。

## 10. 削除手順

1. 削除対象を §6 の基準で特定（最終対応日・状態・is_test・本人申し出）。
2. **誤削除防止の確認（§13）**を実施。
3. Google スプレッドシートの該当行を削除（または匿名化）。
4. 関連する対応メール（Resend 側）や移管先（§8）の要否を確認。
5. **削除実施記録（§12・非 PII のみ）**を残す。

## 11. 複製・書き出し・ダウンロード・ゴミ箱の確認

- 行削除だけでなく、**不要な複製・書き出しファイル・ダウンロードファイル・バックアップ・ゴミ箱（スプレッドシート／ドライブ／端末）**も確認し、不要なものを削除する。

## 12. 削除実施記録に残す項目（**非 PII のみ**）

削除した**問い合わせ本文・氏名・メールアドレス等の PII を削除記録へ再保存しない**。記録は次の非 PII のみ：

- 実施日 / 対象期間 / 削除件数 / 削除理由区分（例：通常1年満了・90日・本人申し出・移管後）/ 実施者 / 確認者 / 例外件数

## 13. 誤削除を防ぐ確認手順

- 削除前に**対象範囲（期間・条件）と件数**を目視確認し、実施者と確認者の**2名で確認**する（少人数運用時は Owner が確認者）。
- 移管理由（§8）や本人からの保留申し出がないかを確認してから削除する。

## 14. 削除依頼への対応

- 開示・訂正・利用停止・削除の請求は、プライバシーポリシー §開示・訂正・削除／お問い合わせ窓口（`info@dokugakulink.com`）で受ける。
- **本人確認**を行い、法令上・業務上の保持理由がなければ**期限前でも対応**する。法令上常に削除できると断定せず、法令に従って対応する。
- 対応後は §12 の非 PII 記録を残す。

## 15. インシデント時の停止・報告手順

- 漏えい・誤送信・不正アクセス等が疑われる場合、**まず保存の受付停止**を検討（例：Vercel の `CONTACT_STORE_URL` を一時的に外す＝保存停止・メールのみに戻す。Owner 操作）。
- 影響範囲（対象件数・項目）を確認し、**Owner・（必要に応じ）個人情報保護委員会・本人への報告**の要否を法令に従い判断する。
- 本書に基づき復元不可能な削除・是正を行い、経緯を記録する。

## 16. Secret・共有トークンを問い合わせ行へ保存しない

- `token`（`CONTACT_STORE_SHARED_SECRET`）はシート列に存在せず、行にも応答にも保存しない（実装・テストで固定）。

## 17. GAS / Vercel ログへ PII を出さない

- サーバーログは `reference`（受付番号）等の非 PII のみ。**メールアドレス・氏名・本文・token を出さない**（`contactHandler` の `logError` は `reference` のみ・`contactStoreClient` は固定エラー・GAS は `internal_error` のみ）。
- Analytics（GA4 / Meta / Clarity / PostHog）へ問い合わせ本文・氏名・メールを送らない。

## 19. Owner による法務・運用確認事項

- プライバシーポリシー追記（本 PR で案を反映）の**法務レビュー**と公開可否。
- 外部・国外取扱い（Google のデータ処理地）の記載要否（公式仕様を確認できた場合のみ・推測で断定しない）。

- 自動削除の導入可否（§20）。

## 20. 自動削除を導入する場合の別承認条件

- **現在のシート構造だけでは最終対応日を機械的に判定できない**（`responded_at` は手動・未対応行は空）。**推測による自動削除は実装しない**。
- 自動削除を導入する場合は、次のいずれかで起算日を確実に記録できるようにする（**今回は GAS・シート構造を変更しない＝別フェーズ提案**）：
  - `status`（対応状態を確実に更新する運用）
  - `lastRespondedAt`／`resolvedAt`（最終対応日を明示的に記録する列）
  - `deleteAfter`（削除予定日を保存時または対応完了時に計算して記録する列）
- 導入は **Owner の別承認**を要し、削除ロジック・テスト・ロールバック・誤設定時の停止条件を設計してから行う。
