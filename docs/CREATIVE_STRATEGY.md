### Design Principles（本書全体の前提）

- **User Value First**：「アプリを売る」ではなく「宅建受験者の不安を解消し、必要な人へ価値を届ける」で設計（§4/§13/§15）。
- **Evidence First**：断定しない。`Fact → Hypothesis → Test → Learning` で整理（§5）。
- **Competitor Independent**：「○○アプリより優れている」等は禁止。判断軸はユーザー課題・価値・独自仮説（§10/P11）。

## 1. Purpose

- **広告クリエイティブの役割**：広告は「素材」ではなく**ユーザー価値仮説を検証する道具**。
  「合格ナビ／合格までの現在地が分かる」等の価値が、宅建受験者に *事前登録* という行動を生むかを確かめる。
- **F3 実験との接続**：本書は `F3_AD_TEST_STRATEGY.md` の仮説 H1–H4・Phase 設計・評価優先順位に従う下位設計。
  F3 が「何を検証するか」、本書が「どの表現で検証するか」を定義する。
- **North Star との関係**：North Star＝ユーザーの喜び（量×質）。広告指標は代理にすぎない。
  評価は **`waitlist_submitted > CTR > CPC`**（KPI_SYSTEM：Conversion > Leading）。登録＝価値が行動を生んだ最良のシグナル。

## 2. Target User Understanding（競合分析ではなくユーザー課題ベース）

実 LP（`UkareruLP.tsx`）の記述を事実源とする。

```yaml
誰に届けるか:      働きながら独学で宅建（宅地建物取引士）合格を目指す受験者。
どんな不安があるか:
  - 「今の自分が合格に近づいているか分からない」（見通しの不安）
  - 「独学で次に何をすればいいか分からない」（優先順位の不安）
  - 「暗記しても忘れる／続かない」（継続の不安）
現在の行動:        市販テキスト／過去問アプリ／通信講座で独学。進捗と現在地が見えず離脱しやすい。
未解決課題:        合格までの現在地・今日やるべき学習が可視化されていない。
ウカレルが提供する価値:
  - 今日やるべき学習と「合格までの現在地」が分かる（合格ナビ）
  - 今日の15問で、すきま時間でも積み重ねられる（低負荷継続）
  - 解説で「なぜそうなるか」まで理解できる（理解）
```

## 3. Message Architecture

### Core Message（会社が届ける価値）

> **独学でも、今日やるべき学習と「合格までの現在地」が分かる。**

＝ 見通しの不安を解消する"合格ナビ"。誇張でなく、LP の中核メッセージと一致。
これは**会社が届ける価値そのもの**であり、検証対象ではなく前提（会社の約束）。

### Supporting Messages（H1〜H3：ユーザー心理を検証する広告仮説）

Core Message（会社が届ける価値）と、H1〜H3（その価値を**どのユーザー心理に、どの表現で当てると
登録行動が生まれるか**を検証する広告仮説）は役割が異なる。Core は前提、H1〜H3 は検証項目。
特に **H1 は「合格可能性が分かる」という表現がユーザー心理に響くかを検証する仮説**であって、
Core Message の言い換えではない。

| ID | メッセージ | 伝える価値 | 想定ユーザー心理 | 検証目的 |
|----|-----------|-----------|-----------------|---------|
| **H1** | 「自分の合格可能性が分かる」（安全表現＝「合格までの現在地が分かる」） | 見通し・現在地の可視化 | 「受かるのか分からない」不安の解消 | 見通し訴求が登録行動を生むか |
| **H2** | 「15問だけ。」（LP変体：今日の15問） | 低負荷・続けやすさ | 「続けられるか不安」への安心 | 低負荷訴求が登録を後押しするか |
| **H3** | 「忘れた頃に、もう一度出題」 | 想起・復習設計（忘却対策） | 「暗記しても忘れる」挫折感への解 | 仕組み訴求が差別価値になるか |

> **表現上の注意**：「合格可能性が分かる」は"予測の断定"と誤認されうる。広告表現では
> **「合格までの現在地／今の位置が分かる」を安全な既定表現**とし、H1 の「可能性」文言は
> 誤認リスクを避けた範囲で検証する（§7 Guardrails）。

## 4. Message Testing Framework（F3 仮説と接続）

各メッセージを `Fact → Hypothesis → Test → Learning` で整理。First Touch は **Acquisition Memory（初回接触の記録・関連性）** であり因果ではない。

### H1 — 見通し／現在地
```yaml
Hypothesis:        「合格までの現在地が分かる」価値は、独学者の"見通しの不安"に響き登録行動を生む。
Expected_behavior: 広告クリック → LP 到達 → 事前登録。
Measurement:       utm_content別 waitlist_submitted（最優先）→ CTR → CPC。GA4/PostHog（first-touch）+ Meta ad単位。
Success_signal:    他訴求より一貫して高い登録関連性（＋補助的に高 CTR）。
Failure_signal:    クリックは来るが登録に繋がらない／訴求間で差が出ない。
```

### H2 — 低負荷「15問だけ。」
```yaml
Hypothesis:        「1日15問」の軽さが"継続の不安"を下げ、登録の心理的ハードルを下げる。
Expected_behavior: クリック → 登録。
Measurement:       utm_content別 waitlist_submitted → CTR → CPC。
Success_signal:    低負荷訴求が登録関連性で優位。
Failure_signal:    注目は得るが登録に寄与しない（軽さが価値と結びつかない）。
```

### H3 — 想起「忘れた頃に、もう一度出題」
```yaml
Hypothesis:        忘却対策の"仕組み"提示が、暗記に挫折した層の課題認識に刺さり登録を促す。
Expected_behavior: クリック → 登録。
Measurement:       utm_content別 waitlist_submitted → CTR → CPC。
Success_signal:    仕組み訴求が特定セグメントで登録関連性優位。
Failure_signal:    仕組み説明が広告では伝わりにくく反応が薄い（LP内訴求へ後退）。
```

## 5. Copy Framework（広告コピー作成ルール）

構成は `Hook → Problem → Value → Action`（問題提起 → 価値提示 → 行動誘導）。以下は**枠組みと骨子**であり、勝ちコピーの断定ではない。

```
Hook     一瞬で自分ごと化させる問い/共感（例：独学で「今どこ？」が分からない）
Problem  ユーザーの不安を言語化（次に何を／受かるのか／続くのか）
Value    ウカレルの価値を1つに絞って提示（現在地が分かる／15問だけ／忘れた頃に再出題）
Action   無料の事前登録へ誘導（「無料で事前登録」）
```

ルール：
- 1 クリエイティブ＝1 メッセージ（欲張らない）。検証は utm_content で識別。
- 価格・無料条件は LP と厳密一致（例：月580円／30日無料／無料期間終了で自動課金しない）。誇張・省略で誤認させない。
- 断定禁止（「絶対受かる」「必ず続く」等）。事実と便益のみ。

## 6. Visual Direction（画像制作前の方向性）

```yaml
世界観:        静か・誠実・前向き。余白を活かし、一瞬で1つの価値が伝わる。信用第一（過剰演出をしない）。
色:            LP と整合する落ち着いた基調（信頼感）。ブランド既定に従い、原色の煽り配色は避ける。
UI利用方針:    実際のアプリUI（合格までの現在地／今日の15問／解説）を"そのまま"見せる。
               未実装機能・架空の数値・偽の画面は使わない（No Fabrication）。
人物利用方針:  **人物を写さない**（ブランド記憶辞典：写真は人を写さない・名詞タイトル）。
               成功者の顔・合格者演出でユーザーを煽らない。
情報量:        1枚1メッセージ。文字は最小限。3秒で「何のアプリで、何が分かるか」が伝わる。
一瞬で伝える要素:
  - 何のアプリか（宅建・独学の学習アプリ）
  - 中心価値1つ（現在地／15問／再出題のいずれか）
  - 次の行動（無料で事前登録）
```

## 7. Brand Guardrails

### 禁止表現
- **合格保証**・合格を確約する表現
- **合格率を誤認させる表現**／未確認・根拠のない数字・架空の実績
- 「合格可能性が分かる」を"予測の断定"と誤認させる使い方（→「現在地が分かる」を既定に）
- 不安を**過剰に**煽る表現（恐怖訴求で登録を強要しない）
- **競合比較**（「○○アプリより優れている」等）
- 価格・無料条件の誤認（無料期間・課金条件は LP と厳密一致）

### 推奨表現
- 透明性（できること/できないことを正直に）
- 学習者支援・伴走の姿勢
- 前向き・成長実感（"できるようになる"手応え）
- 事実ベースの便益（現在地が分かる・15問で続く・解説で理解）

## 8. Creative Test Plan（F3 Phase 接続）

`F3_AD_TEST_STRATEGY.md` の Phase 設計に従う。数値閾値は設定しない（CD-4 DEFERRED）。

| Phase | 何を学ぶか | 判断基準（相対シグナル） | 次アクション |
|-------|-----------|------------------------|-------------|
| **Validation** | どの価値仮説（H1/H2/H3）が登録行動を生むか | utm_content別 waitlist_submitted の相対差＋ファネルの健全性 | 差が出れば Winner Discovery へ／出なければ仮説差替え（§11 失敗も学び） |
| **Winner Discovery** | より強いユーザー価値シグナルを示す訴求の発見（"勝ちクリエイティブ"の断定ではない） | 一貫して高い登録関連性（＋補助 CTR）を示す訴求 | より強い価値シグナルの訴求を選び Optimization へ |
| **Optimization** | より強い価値シグナルを示した訴求での獲得効率 | Meta 最適化に足る転換量が得られるか | Pattern B（最適化）へ移行（L3 判断） |
| **Scale** | 効率を保ったまま量を伸ばせるか | 成果の安定 | 予算拡大を提案（HIGH/L3＝CEO 承認・実データ後） |

各 Phase 遷移は F3 §7 Success/Failure Criteria のシグナルで判断。

## 9. Future Creative Production Input（将来の画像制作の入力条件）

実制作に着手する際（別 Sprint・別承認）に満たす条件。

```yaml
必須要素:
  - 中心メッセージ1つ（H1/H2/H3 のいずれか）と対応する utm_content 命名
  - 実アプリUIの正確な画面（現在地／15問／解説）
  - 無料事前登録への明確な導線（正本URL /landing/takken）
  - 価格・無料条件を出す場合は LP と厳密一致
避ける要素:
  - 人物写真・合格者演出、架空数値・合格率・実績、競合比較、過剰な不安訴求
必要素材:
  - 実UIスクリーンショット（最新ビルド）、ブランド準拠の配色・余白テンプレート
レビュー観点:
  - Brand Guardrails 準拠（§7）／No Fabrication／価格・無料条件の正確性
  - 1枚1メッセージ／3秒で価値が伝わるか／utm_content が計測と一致するか
  - ブランド正本（記憶辞典）と LP 表現との整合
```
